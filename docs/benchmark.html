Methodology

  • Dataset: 1,000,000 records written in key order, 12-byte keys (key_%08d), 61-byte values; reads, updates, deletes and exists checks use random keys
  • Runs: 5 runs per engine, alternating SNKV / SQLite, each on a fresh database file; the mean ops/s of the 5 runs is reported. Deletes (5,000 ops) and mixed (20,000 ops) are short and vary most between runs
  • Config: WAL journal mode, synchronous=NORMAL, 2000-page (8 MB) page cache, 4096-byte pages — identical for both engines
  • SQLite schema: CREATE TABLE kvpairs (key BLOB PRIMARY KEY, value BLOB NOT NULL) WITHOUT ROWID — single B-tree keyed on the same field, prepared statements for all DML
  • Build: both engines on the same SQLite 3.51.2 core, gcc 15.2 -O2 (SNKV: make BUILD=release)
  • WAL checkpoints: both engines auto-checkpoint (PASSIVE) once the WAL holds 1000 pages — SQLite by default, SNKV by its default walAutoCheckpoint
  • Transactions: sequential writes commit every 1,000 rows; updates, deletes and the mixed workload each run in one transaction; bulk insert writes 1M rows in one transaction
  • Memory: both use the same pager and page cache (2000 pages); peak RSS was not re-measured for this run
  • Platform: AMD Ryzen 7 6800H, Linux 6.18 (WSL2), database files on tmpfs — results measure engine CPU cost, not disk speed
Analysis

Where the Difference Comes From

SNKV and SQLite use the same B-tree storage engine at the bottom. Every performance difference comes from what each layer adds on top of it.

Parsing & planning: done once
The SQLite benchmark uses prepared statements, so SQL is parsed and planned once, not per operation. The remaining per-call cost is binding, stepping and resetting the statement, plus encoding and decoding SQLite's record format — SNKV skips all of that and calls the B-tree API directly.
Reads: about 2.3–2.5×
Point reads and exists checks show the largest gap. The B-tree work (one seek) is small, so SQLite's per-statement overhead is a large share of each call — and SNKV's cached read cursor avoids opening a cursor per lookup.
No VDBE interpreter
SQLite compiles queries to bytecode run by a virtual machine. SNKV calls compiled C functions. No bytecode dispatch loop on the critical path.
Cached read cursor
SNKV keeps a persistent read cursor open per column family. SQLite opens and closes a new cursor for each statement. Cursor open/close touches the pager — SNKV skips it on every read.
Writes: 1.0–1.2×
For inserts, updates and deletes the B-tree write itself (page changes, WAL frames, rebalancing) is most of the cost and is identical in both engines, so the layer above matters less.
WAL auto-checkpoint: same rule as SQLite
Both engines checkpoint the WAL once it reaches 1000 pages, so neither pays for an oversized WAL. Before SNKV did this (it opens the B-tree directly, so SQLite's built-in hook was never installed), its WAL grew to the size of the database and every page-cache miss had to search a large WAL index — that alone made SNKV 3–10% slower than SQLite on the mixed workload and cost 8–16% on reads.

Run It Yourself

Both benchmarks are open source. Clone and build to reproduce results on your hardware.

C benchmark — SNKV

# From the SNKV repo root (optimised build, -O2)
make BUILD=release tests/test_benchmark
./tests/test_benchmark

C benchmark — SQLite comparison

# https://github.com/hash-anu/sqllite-benchmark-kv
git clone https://github.com/hash-anu/sqllite-benchmark-kv
cd sqllite-benchmark-kv
make sqlite_benchmark      # SQLite 3.51.2, -O2
./sqlite_benchmark
